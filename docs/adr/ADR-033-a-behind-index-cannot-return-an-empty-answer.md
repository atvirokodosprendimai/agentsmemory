# ADR-033: A behind index cannot return an empty answer to a population gap

**Status:** Proposed (rev. 6 — the above-cap rebuild trigger is corroborated by an index-ingested watermark with hysteresis, and the qdrant exactness premise is a stated verification duty; R4's relabel clause is qualified qdrant-only and its deletion target named; the sqlite "untouched" claim is made precise; `Checked`'s redefinition is named; the surface gap is stated. rev. 5's corroboration read the same cached datum twice, its relabel clause named a command that refuses non-qdrant backends, and its "four call sites" were five)
**Date:** 2026-08-24
**Owner:** unassigned
**Spec:** None — no spec stage
**Cross-references:** ADR-007 (the "number must mean what it says" principle, extended from the eval onto the served path); ADR-015 (the index must not outlive the wing it indexed — this governs the index falling *behind* it instead); ADR-025 (executable-contract axes); internal/palace/indexdrift.go + cmd/server/doctor.go (the detection machinery this ADR's R3 surfaces where the protocol already looks); reconcileChromem in cmd/server/main.go (the boot repair this ADR makes honest about partial fall-behind); docs/postmortems/2026-08-21-absorb-preserved-an-emptiness-it-should-have-filled.md (population absence) and the merge-relabel postmortem referenced by ADR-015 (payload drift — explicitly *not* this ADR's mechanism's domain, see Out of Scope)
**Invalidates:** the operator guidance that says `am_recompute_graph` rebuilds the search index (it cannot — it touches hallways and tunnels only; the empty-search recovery is reconcile/rebuild)

## Context

The palace has twice shipped a memory an agent could not reach, and both times every instrument the operator could run reported success. Those are **two different defects**, and this ADR must not blur them:

1. **Population absence** — the index holds no point for a memory that exists in the source of truth. This ADR's four rules govern this one.
2. **Payload drift** — a point exists but carries a stale `wing` label, so it answers the wrong wing or nothing at all. This was the measured 2026-08-21 merge-relabel incident: 13/359 points, *counts equal*, every health check green. `IndexDrift` exists to detect it (in *both* halves — a stale source of truth makes the drift unreachable again after the next sync). This ADR does not fix drift; R3 makes it visible and R4 names its recovery (a payload relabel, not a rebuild). The division of labour is explicit so no reader inherits a false safety claim.

**What the tree already has (this ADR builds on, does not re-invent).**
`IndexDrift` (internal/palace/indexdrift.go) compares every stored point's payload wing against the wing its drawer lives in, per store half (source of truth and index), flags `Missing` points, counts `Pending` first-embeddings as a queue rather than a fault, and is deliberately read-only. `doctor` runs it with the explicit charter: *"Doctor exists for silent failures that normal requests and health checks can miss."* `reconcileChromem` repairs a wholly-empty index namespace at boot from the SQLite source of truth. The drift repair already exists too: `sync --repair-payload` (`repairNamespacePayload`, cmd/server/sync.go:130) patches the `wing`/`room` payloads from the drawer rows on **both** halves via `Hybrid.SetPayload` — deliberately "not a re-embedding: the vectors are fine, only their labels are missing", and targeting the Hybrid precisely so a stale source-of-truth half cannot re-apply the stale payload over the repair (sync.go:138).

**What is still open, and why it is the same defect one level down.**

1. **Partial fall-behind is invisible.** `reconcileChromem` checks `indexed > 0` and otherwise continues — a namespace at 800 of 1000 points boots clean and nothing reports the 200 missing. It repairs only the *chromem* branch; the qdrant branch of `buildVectorStoreWith` has no boot reconcile at all.
2. **The drift number is not where the protocol already looks.** Every session opens with `am_status`; the health number lives only in `doctor`, a command an operator must remember to run.
3. **`RecomputeGraph` reports what it computed, not what it wrote.** `res.Hallways += len(halls)` and `res.EntityTunnels = len(entityTunnels)` accumulate computed counts; a write that lands fewer rows is indistinguishable from success.
4. **A behind index can answer empty by design.** `Hybrid.Search` is served by the index only. This applies to the Hybrid backends (chromem, qdrant) — the default backend (`VectorBackendSQLite`, config.go:326) serves search directly from the source of truth and has no separate index to fall behind, so it cannot exhibit this defect at all. "The SoT only stores, it does not serve production queries" (hybrid.go:63) is true only for the Hybrid half of the deployment space.
5. **The guidance names the wrong tool.** The 2026-08-21 recovery was attributed to `am_recompute_graph` in the palace drawer `23f9aed8` and the infrawei AGENTS.md first-aid. The code shows it cannot rebuild a search index; the real recovery is the startup reconcile or a deliberate rebuild. A correlation was recorded as a mechanism.

**The reframing (TRIZ/ARIZ), narrowed.** The apparent contradiction — detection must be *complete* yet *cost nothing* — dissolves when the goal becomes the Ideal Final Result scoped to the defect this ADR governs: **an index that has fallen behind its source of truth in population cannot return an empty answer, and its coverage is visible in the call every session already makes.** Verification rides flows that already happen (the write, the mandated first call); the cache stops being able to lie by degrading to the truth; the wrong guidance is deleted rather than corrected. Payload drift is a separate ideal-final-result (IndexDrift's) and is out of this ADR's mechanism.

## Decision

Four rules. The first three are structural; the fourth is a deletion.

**R1 — Verification rides the write.** `ReplaceWingHallways` and `SaveTunnels` return **both legs'** affected-row counts from the write transaction — the delete leg and the insert leg for `ReplaceWingHallways` (delete WHERE wing, then batch insert — graph.go:75), the upserted rows for `SaveTunnels` (graph.go:170) — each capturable inside the transaction callback (each gorm statement carries its own `RowsAffected`). `RecomputeGraph` compares the **insert leg's** count — not the sum; the delete leg exists only to be excluded — against what it computed, and returns an error naming the wing (hallways; `SaveTunnels` is team-wide with no wing, so tunnels name the recompute scope instead) and expected/landed counts on mismatch. `RecomputeResult` reports *verified* counts. No read-back query exists. The power is a wiring-regression net (both writes are single batch transactions; a mismatch means driver-level silent row loss), which is the honest scope.

**R2 — A behind index cannot answer empty.** Scope: the Hybrid backends (chromem, qdrant); the default sqlite backend is **behaviorally** untouched — it serves from the source of truth and no serving behavior changes, but its `Search` signature still changes to satisfy the interface (`StaleIndex:false` always), so "untouched" means behavior, not signature. `Hybrid.Search` compares the index population against the source-of-truth population before serving (counts; see Implementation for the primitives and their cost bounds). When `indexed < expected` — **including zero** — it:
- serves the query from the source-of-truth vector path (the `sqlitevec` search backend — the same backend the default deployment serves from, so this is not new territory for it),
- marks the result `stale_index:true` via the return type: the `VectorStore.Search` interface itself returns `SearchResult{ H []Hit; StaleIndex bool }`. The flag needs a carrier, and it must be reachable from serving — every production caller consumes the interface, so a wrapper on the concrete `Hybrid` would be bypassable and dead at the seam; the ripple (three backends, five call sites — memory_search.go:76, mine.go:322, service.go:1275, eval.go:1149 and 1375, plus storetest/conformance.go) is the point, and `store.Hit` today is ID/Score/Payload only,
- triggers an async rebuild, single-flighted per namespace (concurrent queries observe one rebuild; none runs synchronously in the request path, in any branch).

The empty case is deliberately unified with the partial case: an index with nothing is exactly where source-of-truth hits equal rebuilt-index hits, so a synchronous rebuild in the request path would only buy a stampede. Equal counts → serve from the index, behavior unchanged. `indexed > expected` → reported (R3's raw fields and the reconcile report — never a search action).

The degraded state is time-bounded: the count cache is invalidated on every write (`Upsert`/`Delete`/`SetPayload` — a failed index write must not be masked by a cached equal-count pair) and on rebuild completion, so the behind-index window is one write, not one TTL. The rebuild itself can race a concurrent write (it snapshots `AllPoints` then upserts chunked with `wait=true`; a write landing mid-rebuild can be overwritten by the older snapshot value). This is the first time `Rebuild` runs alongside live serving, so the ADR acknowledges the race and the mitigation direction: after the rebuild completes, reconcile the count cache and re-check the comparison (the next query re-runs it), and where rows carry a timestamp, skip-upsert stale snapshots so last-write-wins favours the live write. The race's residual is a stale-but-flagged window, not a silent empty answer. A **failed** rebuild must not re-run on every degraded query: single-flight dedups concurrent attempts but not sequential ones, so a failed rebuild gets a cooldown (per-namespace state in `Hybrid`; the duration is a parameter, start in minutes) and re-triggers only after a subsequent write or the cooldown elapses.

**R3 — `am_status` reports serving coverage, defined over the half that serves.** One number per workspace, per namespace (drawer namespace and closet namespace reported separately — coverage blends namespaces, but the recovery tools act per namespace, so the breakdown must be visible). Coverage measures the **index half only**: the source-of-truth half's drift does not depress a serving number (it is invisible to serving until the next sync, and is reported separately in the raw fields).

`coverage = (expected − index_missing − index_mislabelled) / expected`, clamped to [0, 1]

where the terms are pinned to the accounting that returns them. `expected = EmbeddedDrawers + EmbeddedClosets`: the embedded halves of `DrawerWings` (which returns the embedded map and the pending list as **separate** values — repo.go:754) and of `ClosetWings` (with the `embedded_at` filter this ADR adds). That is every row that should hold a point — all rows minus pending — excluded **once, by construction**. There is deliberately no `− pending` term: `DrawerWings` already excludes pending from its map, so subtracting it again double-subtracts and every busy palace reads coverage < 1; and pending > embedded would drive the denominator negative, inverting the corruption signal. `index_missing` is the drawers/closets with no point in the index half; `index_mislabelled` is the points in the index half whose payload wing differs from the row's. A denominator of zero (nothing embedded yet) is coverage 1.0 — vacuously healthy. The residence of the row counts is named, not left to the implementer: `DriftReport.Checked` is today one combined number (`len(embedded drawers) + len(all closets)` — indexdrift.go:112,148), and the closet filter this ADR adds silently redefines it, so the report splits `Checked` per namespace and per half (drawers vs closets) and the per-namespace `expected` and `indexed` live there; the am_status handler reads the report rather than re-running repo queries.

A note on the two senses of the population check: R2's search gate compares the index point count against the source-of-truth point count, while R3's coverage derives `expected` from rows. The two coincide absent orphans and mid-embed windows; where they diverge, the raw fields make the divergence visible instead of silently blending it. The clamp at 0 is defensive — `missing` and `mislabelled` are disjoint subsets of `expected`, so coverage already lies in [0, 1] and a negative value is reachable only through a counting bug, which the clamp stops from displaying as a negative number. The clamp must not hide data: `am_status` reports the raw fields alongside (indexed, expected, missing, mislabelled, pending, per namespace), so corrupted inputs and an over-count (`indexed > expected` — orphans, which the formula skips) both remain visible in the mandated first call even though the formula saturates. One caveat on the over-count: the embed worker upserts a vector *before* stamping `embedded_at` (deliberate crash-idempotency, embedpending.go), so during a normal async-embed batch the index briefly holds points whose rows are still pending — that window reads `indexed > expected` without being orphans. The over-count branch reads the pending field alongside: a point whose row is still pending is not an orphan, and the report only flags `indexed > expected` that is not explained by the pending read at report time — a snapshot cannot observe duration, so the pending read is the operative rule, and a second read after the embed batch drains disambiguates.

**R4 — The guidance is deleted, not corrected, and split by cause.** The infrawei AGENTS.md first-aid and the `23f9aed8` attribution are replaced by one line: *"palace health = `am_status`; coverage == 0 → restart (reconcile, chromem only); 0 < coverage < 1 with missing points → rebuild the index; drifted > 0 → relabel the payloads (`sync --repair-payload`, qdrant only)."* The clauses name tools that can actually act on the cause — and only tools that exist **and run on the backend they are named for**:
- **coverage == 0 → restart.** A restart repairs *empty* namespaces via reconcile — and only on chromem; the qdrant branch has no boot reconcile, so on qdrant a coverage of 0 resolves to the rebuild clause (the first search's R2 self-heal or an explicit rebuild) instead.
- **0 < coverage < 1 with missing points → rebuild the index.** `Hybrid.Rebuild` replays the source of truth, so it fixes absence.
- **drifted > 0 → relabel the payloads.** Rebuild *cannot* fix drift — it replays the source of truth, which carries the drifted payloads. Drift recovery is a payload relabel, not a re-embedding: `sync --repair-payload` (`repairNamespacePayload`) patches the `wing`/`room` payloads from the drawer rows on both halves via `Hybrid.SetPayload` — the tree's own words are "deliberately not a re-embedding: the vectors are fine, only their labels are missing, and on a large palace the difference is minutes against days", and a re-embed is both nonexistent in the tree and the documented rejected option for a label change (the vector is already correct — the text did not change; ADR-015's merge decision and the 2026-08-21 postmortem). Named here so the guidance never points drift at the one tool that is guaranteed not to act on it (rebuild) or at one that does not exist (re-embed). Two honest limits on this clause: `sync` hard-refuses non-qdrant backends (sync.go:52 — with sqlite the source of truth IS the index, and chromem refills an empty index at boot), so the relabel clause is **qdrant-only**; chromem drift recovery awaits the wrapper in Follow-ups. And `repairNamespacePayload` pages `repo.List` — drawers only — so closet drift, which R3 now reports per-namespace, is not yet repairable by this tool; wiring the same relabel for closets is implementation work.

**Composition.** The causes co-occur, so the clauses compose rather than exclude. `0 < coverage < 1` with `drifted > 0` is rebuild **then** relabel — rebuild first replays the source of truth and returns the missing points *with* their drifted payloads, so relabel runs after it. `coverage == 0` with points present (an all-mislabelled index) is the drifted case — restart's reconcile only fills empty namespaces (`indexed > 0 → continue`) and would no-op, so relabel applies. An empty index (`coverage == 0` from all-missing) with source-of-truth drift is the same chain — rebuild fills it, relabel cleans it — named here so no operator spends one wasted rebuild before relabel. The one-line reads like if-else; the bullets and this paragraph are the composition.

Recommending restart for the partial case or rebuild for the drifted case would reproduce the wrong-tool correlation this ADR exists to kill; the split is the point of the one line. Two things are stated here rather than left implicit: the one-line names server/CLI surfaces (restart, rebuild, `sync --repair-payload`) while palace operators hold the `am_*` surface — the wrapper that exposes these is a stated follow-up, and the one-line is honest about the surface it names — and the deletion is **external**: the first-aid lives in the infrawei project's AGENTS.md, so the change set names that path and lands the edit with the merge. A counter-drawer records the mechanism; the recompute-as-cure myth dies by having nothing to point at.

## Implementation

TDD, per repo protocol — RED first; each test must fail when the wiring it guards is deleted.

- `TestSearchFallsBackWhenIndexBehind` — index at 7/10 → the query returns the source-of-truth hits with `stale_index:true` (asserted on the interface's return — the flag's carrier), never an empty result.
- `TestSearchDoesNotBlockWhenIndexEmpty` — `indexed == 0` serves immediately from the source of truth and the rebuild is async: assert no synchronous `Rebuild` call on the request path (elapsed or call count). This is the anti-stampede test.
- `TestRebuildBackoffOnFailure` — a failed rebuild does not re-run per degraded query: within the cooldown, degraded queries serve without triggering another rebuild (call count observed); a subsequent write re-arms it. Fails when the backoff wiring is deleted.
- `TestApproximateCountAloneDoesNotTriggerRebuild` — above the cap, a lagged approximate count alone (a read below the watermark, or the same cached pair read twice) does not trigger a rebuild; only a count at-or-above the watermark and below `expected` does. Fails when the corroboration is deleted.
- `TestMinimumInterRebuildInterval` — two consecutive triggers within the interval observe one rebuild (call count), and a post-rebuild exact-count refresh (below the cap) re-decides on a fresh number rather than the same lagged one.
- `TestCountCacheInvalidatedOnWrite` — an index `Upsert` failure followed by a search within the TTL does not serve from the behind index: the write invalidates the cached count pair.
- `TestRecomputeGraphVerifiesWrittenCounts` — a repo whose write returns fewer rows than computed makes `RecomputeGraph` error with wing (or recompute scope, for tunnels) + expected/landed.
- `TestReconcileReportsPartialDrift` — 7/10 at boot → the reconcile report names the 3 missing; `TestDoctorIndexFailsOnPartialDrift` keeps the symptom layer failing. `TestReconcileReportsOverCount` — `indexed > expected` at boot → the report's over branch names it (claimed only when it has a guard test).
- `TestAmStatusReportsCoverage` — the status carries the formula, including the pending-only palace reading 1.0, not a division error.
- `TestCoverageExpectedIsEmbeddedCounts` — a mixed palace (embedded + pending + missing) reads coverage from embedded counts: pending excluded once, no double-subtraction. Fails when the term mapping is re-blended (e.g. subtracting pending from a map that already excludes it).
- `TestCoverageUsesIndexHalfOnly` — source-of-truth-half drift does not depress the serving number; a point drifted in both halves depresses it once (per-half counters, not the conflated `Total`).
- `TestCoverageClampsToUnitInterval` — a deliberately corrupted report (`missing + mislabelled > expected`, unreachable from the pinned accounting but possible from a counting bug) reads 0, not a negative number; the raw fields still expose the corrupted inputs; over-count (`indexed > expected`) reads 1.0 while the raw fields show it.
- `TestIndexDriftCountsPendingClosets` — a closet awaiting first embedding is `Pending`, not `Missing` (wires closet pending into the drift accounting; fails when the wiring is deleted).

New primitives, named because "both are indexed COUNTs" is not true today:
A deliberate asymmetry sits on the seam: `Count` is on the mandatory `VectorStore` interface (now 8 methods — a real widening against "keep interfaces small") while `ApproximateCount` is the optional `ApproximateCounter` refinement. Every backend genuinely can count exactly, so the population contract is mandatory; the approximate count is an optimization some backends offer, so it is opt-in. The two counts landing on opposite sides of that line is the point, not an accident: a caller may rely on `Count`, and may only discover `ApproximateCount` by type-asserting for it.

- A `Count(namespace)` on both halves — sqlitevec (`SELECT COUNT` on the source of truth) and the `VectorStore` interface implemented by qdrant. qdrant's count contract must be verified against the pinned qdrant version during implementation: `count_points` is exact for unfiltered namespace counts (the shape this check uses) and approximate only under a filter, in which case `exact:true` is the accuracy/cost lever. The contract is written for the unfiltered shape: exact counts run only for namespaces under a documented size cap, and above it the check uses the approximate count with the quality flagged (`count_quality: "sampled"` in the raw fields — the caveat needs a carrier like any other flag), mirroring the tree's `SamplePayloadCoverage` sampling precedent in spirit ("a hundred are enough") though that precedent returns a *proportion*, so the fallback is an estimate, not a sample extrapolation. An approximate count **alone** never triggers a rebuild, and consecutive degraded reads are not a corroboration either — the count pair is cached for the TTL, so two queries read the same datum unless a write separated them. The corroborating signal is the **index-ingested watermark**: per namespace, the index count recorded at the last successful write to that namespace, updated on `Upsert`/`Delete`/`SetPayload` and on rebuild completion. A read at-or-above the watermark that is still below `expected` is a genuine deficit (the index ingested fewer than the source of truth holds) and corroborates the trigger; a read *below* the watermark is a lagged count (it should trail the last ingest, not precede it) and suppresses the trigger until the count catches up. A rebuild — false-triggered or not — cannot repeat in a loop: a minimum inter-rebuild interval per namespace (independent of the failure-only cooldown) plus, below the cap, a post-rebuild exact-count refresh, so the decision after a rebuild is made on a fresh number rather than the same lagged one. The comparison runs once per query against a cached count pair (TTL), invalidated on write and on rebuild completion; the healthy path pays one cached count pair, not one per widening round (search calls `Hybrid.Search` up to 4×/query via `k *= 2`).
- `IndexDrift`'s `DriftReport` gains per-store-half **and per-namespace** counters (`IndexMissing`, `IndexMislabelled`, `SotMissing`, `SotMislabelled` — eight values, drawer and closet namespaces counted separately) so coverage and its per-namespace breakdown are derivable from real aggregates rather than the conflated `Total` (missing + mislabelled across both halves) or the sampled listing; closet pending is wired in (repo.go's `ClosetWings` currently selects without the `embedded_at` filter, so pending closets read as missing; `PendingClosetCount` already exists and is used by `Service.PendingCount` — what it lacks is a role in drift accounting, which this wiring gives it); and `Checked` splits per namespace and per half (drawers vs closets) so the per-namespace `expected`/`indexed` row counts have a named residence — today `Checked` is one combined number (indexdrift.go:112,148), and the closet filter silently redefines it, so the split is stated, not accidental.
- The `stale_index` flag's carrier is the `VectorStore.Search` interface's return type — `SearchResult{ H []Hit; StaleIndex bool }` — chosen over a parallel method because every production caller consumes the interface: the flag is reachable from serving or it is not reachable at all.

Files: `internal/store/store.go` + `internal/store/sqlitevec/sqlitevec.go` + `internal/store/qdrant/vector.go` + `internal/store/chromemvec/chromemvec.go` (Count + cost bound + SearchResult return), `internal/store/hybrid.go` (R2, single-flight rebuild, count-cache invalidation, rebuild cooldown, watermark), `internal/palace/memory_search.go` + `internal/palace/mine.go` + `internal/palace/service.go` + `internal/palace/eval.go` (SearchResult call sites — read `.H`) + `internal/store/storetest/conformance.go` (three Search calls), `internal/palace/graphquery.go` + `internal/palace/graph.go` (R1), `internal/palace/indexdrift.go` (per-half, per-namespace counters + closet pending + Checked split), `cmd/server/main.go` (reconcile report with over/under), the `am_status` handler (R3 fields), `doctor` (unchanged symptom layer), `cmd/server/sync.go` — already exists, no change; R4 names it, two test files, one doc, one drawer, and the infrawei AGENTS.md first-aid (external edit, path named in the change set).

## Consequences

- **Positive:** a namespace at 80% is visible at boot and in every session's first call, with the raw counts to tell absence from drift; a recompute that lands half its hallways becomes an error; a search with a behind index returns the truth (degraded, flagged, never blocked) instead of nothing; the operator guidance names tools that actually exist, run on the backend they are named for, and act on the cause they describe (restart for empty, rebuild for missing, relabel for drift — qdrant; chromem awaits the wrapper).
- **Negative:** the Hybrid backends gain a per-query count comparison with a stated budget (one cached count pair per query, invalidated on write); exact qdrant counts are bounded by a size cap — above it the count is a flagged estimate that cannot alone trigger a rebuild (watermark-corroborated); a failed rebuild backs off instead of retrying per query; `doctor --index` keeps failing on drift that used to look clean, so operators with deliberately partial indexes must say so; `am_status` grows several fields (additive, no breaking change); the `VectorStore.Search` return type changes, rippling to three backends and five call sites.
- **Neutral:** the default sqlite backend is behaviorally untouched by R2 (it already serves from the source of truth; its `Search` signature changes with the interface, `StaleIndex:false` always); no storage change, no migration, no re-embed; existing palaces report coverage immediately.

## Out of Scope

- **Payload wing-drift (the 2026-08-21 merge-relabel incident).** R2's population check sails past drift (counts equal); the source-of-truth fallback filters on the same drifted payload; R4's rebuild clause is explicitly *not* for drift. Drift is `IndexDrift`'s detection domain and its recovery is the payload relabel from the drawer rows (`sync --repair-payload`, qdrant only — explicitly *not* a re-embedding: only the labels are missing, the vectors are already right). R3's per-half counters make it visible in `am_status`, and that is this ADR's contribution to it. Stated so no reader inherits a false safety claim.
- Full replay on every boot (startup must not scale with the palace — R2's async rebuild serves the truth while it runs).
- Parallel per-wing recompute (SQLite is a single writer; fanning out the read-only embed work is a separate change).
- ADR-007's remaining eval tasks (unchanged).

## Rollback

R1 and R4 are verification/doc changes (revert, and recompute reports computed counts again). R3 is an additive status field set (a reverted server just omits them). R2 is the only behavioral change: revert `Hybrid.Search` (and the `SearchResult` return) and search is again index-only, which is exactly the status quo ante including its wrongly-empty answers. No storage or schema change anywhere.
